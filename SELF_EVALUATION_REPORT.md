## 5. Framework Evaluation

### 5.1 Spring AI
Not implemented. No `spring-ai` dependency, `ChatClient`, advisors, or `VectorStore` usage exists in `pom.xml` or sources. Marked **Optional Not Implemented**; its 10 points were redistributed to LangChain4j per the scoring rule.

### 5.2 LangChain4j
- **AI Services:** `FraudInvestigationService` (`@SystemMessage` from `prompts/fraud-system.txt`, `@UserMessage`) and `FollowUpAssistant` (`@MemoryId` = caseId).
- **Tools:** `Lc4jEvidenceTools` exposes exactly the 7 allow-listed read-only tools; names verified against `ToolRegistry` at construction.
- **Structured output:** JSON schema resource + tolerant fenced-JSON parser → `RawRecommendation` → `RecommendationValidator` → typed `FraudCaseRecommendation`.
- **Memory:** `MessageWindowChatMemory` (max 12 messages) backed by `JpaChatMemoryStore`; memory ID must match `^CASE-\d{4}-\d{4,}$`; follow-up context assembled only from the requested case's persisted records.
- **RAG:** retrieval is a first-class tool (`retrievePolicyEvidence`) rather than a `RetrievalAugmentor`; functionally equivalent grounding with thresholded Top-K and abstention.
- **Failure handling:** `UnconfiguredChatModel` without API key; `ProcessorUnavailableException`/`InvalidRecommendationException` → `SAFE_MANUAL_REVIEW`; tool error/argument/hallucinated-name handlers return structured safe messages; max sequential tool invocations bounded.
- **Config:** model, key, temperature, token and timeout limits all externalised (`application.yml` / env vars).

### 5.3 Framework Parity
Not applicable — only one AI framework is implemented (deliberate design decision documented in `AGENTS.md` and `README.md`). The framework-neutral `FraudCaseProcessor`/`CaseConversation`/`PolicyRetriever` ports keep a future Spring AI adapter isolated from business services.

## 7. Strengths

1. **Defense-in-depth safety architecture:** read-only tool allow-list with forbidden-keyword start-up assertion, hallucinated-tool-name interception, structured output validation that rejects fabricated evidence/citation IDs and any claim of completed action, mandatory `humanReviewRequired`, and state transitions owned exclusively by `CaseStateMachine`/application services.
2. **Deterministic, traceable evidence layer:** SHA-256-seeded synthetic fixtures guarantee identical inputs → identical tool results; every tool call produces a trace ID, request hash, redacted result, duration metric and provenance-linked evidence items; identical requests are cached per session.
3. **Grounded RAG with honest abstention:** validated policy front matter, section-aware chunking, ACTIVE/effective-date filtering, stale-version dedup, configurable threshold, explicit abstention that forces `MANUAL_REVIEW`, and persisted citations with scores surfaced in the UI.
4. **Strong test and audit posture:** 78 offline tests including labelled scenario suite, failure modes, memory isolation and audit-chain verification; append-only hash-chained audit with a verify endpoint; correlation IDs and redacting logging throughout.

## 12. Final Verdict

**Demo Ready.**

Verified evidence: a clean offline `mvn -B clean verify` (78/78 tests, packaged jar), a complete LangChain4j implementation behind framework-neutral ports, a deterministic evidence/tool layer with full traceability, thresholded policy RAG with citations and honest abstention, mandatory human review with separation of duties, prompt-injection defences, and an append-only audit trail. The two material gaps — no transaction-velocity/amount-deviation tooling and no AML/sanctions screening path — are capability gaps rather than defects, and live-model verification still requires an Anthropic API key. These keep the project short of a flawless score but do not block a demonstration.
